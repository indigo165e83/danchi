# 要件

「何ができるべきか」を領域ごとのファイルにまとめる。

| ファイル                               | 内容                                 | ID の形式    |
| -------------------------------------- | ------------------------------------ | ------------ |
| [concept.md](concept.md)               | コンセプト・どんな体験か・開発の段階 | －           |
| [room.md](room.md)                     | 部屋                                 | REQ-ROOM-xx  |
| [plants.md](plants.md)                 | 植物（育てる・成長）                 | REQ-PLANT-xx |
| [items.md](items.md)                   | アイテム                             | REQ-ITEM-xx  |
| [ai-residents.md](ai-residents.md)     | AI 住人                              | REQ-AI-xx    |
| [non-functional.md](non-functional.md) | 非機能要件と制約                     | REQ-NFR-xx   |

新しい領域が出てきたら、ファイルを1つ追加してこの表に載せる。

## 書き方

- 要件には「何ができるべきか」を書く。「どう実現するか」（具体的な数値や仕組み）は [design/](../design/) に書く
- 全体はこの粒度にとどめ、各段階の詳細は着手直前に design で具体化する
- 各領域ファイルは「ID / 要件」の表にする
- 段階との対応は [concept.md](concept.md) の開発の段階の表で管理し、各要件ファイルには書かない

## 要件IDのルール

要件IDは、テスト条件や Pest のテスト名からも参照する（トレーサビリティ確保のため）。

- 要件IDは「REQ-領域-番号」の形式にする（領域は ROOM / PLANT / ITEM / AI / NFR）
- 非機能要件も `REQ-NFR-xx` とし、すべての要件が `REQ-` で始まるようにする
- 新しい要件には、そのファイルの最後の番号の次を付ける
- 新しい領域を追加するときは、領域名もあわせて決めて上の目次に書く
- 一度付けたIDは変えない。要件を別の領域に移しても ID はそのまま残す
- 不要になった要件は削除せず、先頭に【廃止】と書いて残す

## 範囲外（当面作らないもの）

- 住人同士の自由なメッセージ機能：通報・ブロックなどのモデレーションが必要になるため。当面は定型の挨拶やスタンプのみにする
- 共有花壇の完全なリアルタイム反映：当面はポーリングや足跡表示で十分とする
