# 0003: ドキュメントの管理方法

- 日付：2026-10-04
- 状態：決定

## 背景

開発と並行して、設計書・技術選定・開発時の気づきを残したい。
コードは Public で公開するが、設計書の一部は公開するか迷っている。

## 決定

- ドキュメントはコードと同じリポジトリの `docs/` に Markdown で置く（Docs as Code）
- 構成は目的別（concept / design / adr / test / dev-notes）とし、`test/` の中だけ JSTQB/ISTQB のテストプロセスに沿わせる
- 非公開のドキュメントは、別の Private リポジトリ（danchi-private-docs）を `docs-private/` にクローンして管理する
- `docs-private/` は親リポジトリの `.gitignore` で除外する

## 理由

- 設計とコードを同じコミットで更新でき、内容のずれを防げる
- Claude Code などの AI ツールがリポジトリ内の設計書を参照できる
- 設計・テストの考え方まで見えるリポジトリは、ポートフォリオとしての価値が高い
- GitHub はリポジトリ単位でしか公開／非公開を設定できないため、非公開分は別リポジトリにする必要がある
- `.gitignore` だけで除外すると、履歴・バックアップ・他PCとの同期ができない
- サブモジュールは Public 側に非公開リポジトリへのリンクが表示され、手順も複雑になるため採用しない
- JSTQB/ISTQB はテストの進め方と成果物を扱うもので、開発全体のドキュメント構成は定めていないため、全体ではなく `test/` のみに適用する

## 影響

- Public リポジトリに一度コミットした内容は履歴に残るため、迷うものはまず `docs-private/` に書く
- Claude Code に非公開ドキュメントを読ませる場合は、パスを明示する
