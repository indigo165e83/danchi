# 0003: ドキュメントの管理方法

- 日付：2026-10-04
- 状態：決定

## 背景

開発と並行して、設計書・技術選定・開発時の気づきを残したい。
コードは Public で公開するが、設計書の一部は公開するか迷っている。

## 決定

- ドキュメントはコードと同じリポジトリの `docs/` に Markdown で置く（Docs as Code）
- 構成は目的別（requirements / design / adr / test / dev-notes）とし、`test/` の中だけ JSTQB/ISTQB のテストプロセスに沿わせる
- `requirements/` は領域ごとのファイル（room.md、plants.md など）に分ける。フォルダにはしない
- `design/` は全体に関わる設計を直下に置き、領域ごとの設計は requirements と同じ領域名のフォルダに置く
- 要件IDは「REQ-領域-番号」（例：`REQ-PLANT-01`、非機能要件は `REQ-NFR-01`）とし、振り直さない・使い回さない
- 非公開のドキュメントはリポジトリ直下の `docs-private/` に置き、`.gitignore` で除外する（Git 管理外）

## 理由

- 設計とコードを同じコミットで更新でき、内容のずれを防げる
- Claude Code などの AI ツールがリポジトリ内の設計書を参照できる
- 設計・テストの考え方まで見えるリポジトリは、ポートフォリオとしての価値が高い
- requirements は1領域あたりの分量が小さいため、フォルダにせずファイル単位で十分
- design は領域ごとに複数の設計書が増えるためフォルダで分ける。テーブルや画面は領域をまたぐため全体の設計として直下に置く
- 要件IDを領域ごとの番号にすると、次の番号がその領域のファイルを見れば分かる
- `REQ-` を付けることで、Issue やテスト名の中でも要件だと一目で分かり、検索でまとめて探せる
- 要件を別の領域に移す場合も ID は変えない（テストや Issues からの参照を切らないため）
- GitHub はリポジトリ単位でしか公開／非公開を設定できない。別の Private リポジトリやサブモジュールは手順が増えるため、Git 管理外のフォルダで十分とする
- JSTQB/ISTQB はテストの進め方と成果物を扱うもので、開発全体のドキュメント構成は定めていないため、全体ではなく `test/` のみに適用する

## 影響

- Public リポジトリに一度コミットした内容は履歴に残るため、迷うものはまず `docs-private/` に書く
- `docs-private/` は Git の履歴・他PCとの同期がないため、必要に応じて手動でバックアップする
- Claude Code に非公開ドキュメントを読ませる場合は、パスを明示する
